We should launch the new customer onboarding flow as a small pilot on 2 November 2026 with 20 invited accounts. The pilot should use the current billing integration. Existing accounts should not be migrated, and we should not introduce a new payment method during this pilot. The purpose of this review is to make the launch decision and the operational handoffs clear to the operations team before invitations go out. A broader rollout should be considered separately after the pilot review rather than treated as part of this decision.

When a request arrives, the team should validate it. If validation fails, the result should be an error with a reason. If validation passes, the next step is to attempt payment. If payment is not confirmed, the result should also be an error with a reason. The service should be provisioned only after payment is confirmed, and the customer should then receive a receipt. The request ID should be used to prevent duplicate processing if the same request is submitted again.

Operations should own request validation and triage. Billing should reconcile payment status, while Platform should own provisioning and rollback. Support should handle receipt resend and customer communication. A failed receipt delivery should leave the account active. Support should resend the receipt without charging or provisioning again. This exception matters because a communication failure must not cause the team to repeat a completed payment or create another account.

The readiness check should happen on 28 October, followed by a joint Operations and Billing sign-off on 30 October. Both teams must approve before invitations are sent. The pilot should start on 2 November, and the review should take place on 5 November. The decision about expanding beyond the pilot should be made after that review. Payment-reconciliation coverage outside normal support hours is still an open question and should be resolved before the pilot needs that coverage.

If a payment/provisioning mismatch appears, new invitations should stop. The team should reconcile the mismatch before resuming them. Stopping invitations should not automatically refund payments or delete existing accounts. The team should report the number of requests, confirmed payments, provisioned accounts, and receipts each day at 13:00 UTC. These counts describe activity; they should not be presented as cohort conversion unless the relevant records are linked to one another.

Before the readiness check, Operations should verify invalid-request cases and Billing should test unconfirmed payments, both by 28 October. Platform should rehearse rollback by 30 October, and Support should prepare receipt recovery by the same date. These tasks, the two-team approval gate, and the unresolved coverage question should remain visible in the launch review so that a reader can identify the next action without reconstructing the plan from the process description.
